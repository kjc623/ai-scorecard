# 0006. Content is stored only as ciphertext under per-object keys wrapped by a per-tenant key

Status: proposed
Date: 2026-10-02

Supersedes: ADR 0006 of the pre-brief package ("personal fields are stored as ciphertext under
per-subject keys"). That decision protected fields inside event rows; this one protects the content
store, which is the only tier where the product's promise is at stake.

## Context

Brief §4.4 sets three requirements that jointly determine the design:

- Per-object encryption keys wrapped by a per-tenant key.
- "Where the customer supplies the key, destroying it must destroy the content."
- Content never arrives unsolicited; it crosses only on a granted, per-event request.

Brief §3.3 adds that per-tenant keys are mandatory and that customer-held keys must be supported,
because some buyers require that the vendor cannot read content at all. Brief §3.5 then states the
constraint that makes this a decision rather than a detail: customer-held keys and server-side
full-text search cannot both exist.

## Decision

Content is ciphertext in Blob Storage. Never plaintext, at any tier.

The key hierarchy:

| Level | Key | Held by |
|---|---|---|
| Per object | AES-256-GCM data key, generated by `content-vault` on grant approval | Only in memory, during the request; then only in wrapped form |
| Per tenant | Key-encryption key in Key Vault, or the customer's vault or HSM | `ops.tenant.kek_id` names it; `key_custody` selects the mode |
| Wrapped DEK | Stored in `ops.content_object.wrapped_dek` | Readable only by `sac_vault` |

**Three custody modes, described honestly:**

| Mode | What it actually guarantees |
|---|---|
| `vendor` | Vendor-managed per-tenant key. The vendor can decrypt, under audit. Suitable for tenants whose requirement is contractual rather than architectural |
| `customer_managed` | The KEK lives in the customer's vault and the vendor reaches it by federated identity with `wrapKey`/`unwrapKey`. This means "the vendor cannot read content **without an audited unwrap**" — it is *not* the same as "the vendor can never read content", and it must not be sold as such |
| `customer_held` | The KEK never leaves the customer's HSM. Retrieval requires a customer-side delegation, which cannot meet brief §8's 30-second target unless the customer pre-authorises a time-boxed window |

`content-vault` is the only component holding unwrap rights, and it has internal-only ingress. It is not
reachable from a device or a browser (master doc D7).

Destruction is two operations, deliberately: delete the wrapped DEK **and** delete the ciphertext.
Either alone leaves a gap — a key deleted while the object remains cannot be described as removed in a
receipt, and an object deleted while its wrapped key survives in a database backup has not really been
destroyed.

## Alternatives considered

- **Server-side encryption at rest only (the storage account's own SSE).** Rejected: brief §4.4 requires
  that destroying a customer-supplied key destroy the content, which ordinary SSE cannot express, and it
  leaves the vendor able to read everything.
- **Storing content in the database as `bytea`.** Rejected: it puts the largest and most sensitive
  object class inside the system of record, where every backup, replica and PITR snapshot inherits it.
  The whole point of the boundary in brief §1.1 is that content is a separate lifecycle.
- **One key per tenant, no per-object layer.** Rejected: destroying one object's content would require
  re-encrypting the tenant's entire store, which makes an erasure request a bulk operation.

## Consequences

Easier: an erasure is two row operations rather than a rewrite. Tenant offboarding is one key
destruction. A breach of the database yields labels and pseudonymous references but no content.

Harder: key custody becomes an operational discipline with a recovery window — Key Vault soft-delete
and purge protection mean "destroyed" is not instantaneous, and the actual window must be disclosed in
the erasure receipt rather than assumed away. `customer_held` needs a customer-side component, which is
why v1's export is metadata-and-labels only (master doc Q11).

We now maintain: the key hierarchy, per-tenant key rotation, the `customer_held` delegation path, and a
documented answer to "what happens if the customer loses their key" — which is that the content is gone,
by design, and the erasure receipt is the only remaining record of it.

Revisit if: a customer requires customer-held keys **and** prompt-content search. ADR 0014 already
provides content search for tenants whose custody permits it, and makes the impossible combination
unrepresentable; what it cannot serve is a tenant that insists on both. The answer there is on-device
distributed search — a substantial subsystem, not a configuration change — which is why it is open
question Q15 rather than in v1.
