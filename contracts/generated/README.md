# Generated contract types

These files are generated from [contracts/event-envelope.schema.json](../event-envelope.schema.json).
The schema is the only permitted source of field names; the generated files are build output that
happens to be committed, so that the TypeScript and Go sides of the contract can be reviewed together
and drift is a test failure rather than a discovery.

[ADR 0010](../../docs/adr/0010-the-envelope-is-a-discriminated-union-with-a-closed-kind-registry.md)
is what this directory implements: one record, a common core, per-`kind` required fields, and `kind` as
a closed registry. Adding a kind is an ADR plus a schema change, not an edit here.

| File | Status |
|---|---|
| `typescript/envelope.ts` | generated - do not edit |
| `go/envelope/envelope.go` | generated - do not edit |
| `go/go.mod` | hand-written module definition for the generated Go package |
| `README.md` | hand-written, this file |

Generated by `contracts/tools/generate.mjs` from `contracts/event-envelope.schema.json`
(module path `shadow-ai-capture.invalid/contracts/generated/go`, package `envelope`).

## Commands

```pwsh
# Regenerate both files in place
node contracts/tools/generate.mjs

# Fail (exit 1) if the committed files are not what the schema produces
node contracts/tools/generate.mjs --check

# The whole verification suite: drift, registries, requiredness, unions, Go compile, Go decoder
node --test contracts/tools/

# The generated Go package on its own
$env:GOCACHE="$PWD\.tools\gocache"; $env:GOPROXY="off"; $env:GOTOOLCHAIN="local"; $env:GOFLAGS="-mod=mod"
cd contracts/generated/go; go build ./...; gofmt -l envelope/envelope.go
```

Zero dependencies: the generator and the suite use only the Node standard library, and the Go package
imports only `bytes`, `encoding/json`, `fmt`, `regexp` and `strings`. Neither needs the network, which
this host does not have.

`node --test contracts/tools/` reaches the suite through `contracts/tools/index.js`: Node 22 treats a
positional test path as a glob or a file, not as a directory, so without that entry point the directory
form fails with `Cannot find module .../contracts/tools` and runs no tests at all. Running
`node contracts/tools/verify.mjs` directly is equivalent.

## What the generator derives from the schema

The contract has two shapes (what a device may send, and what is stored, which adds the
server-assigned `received_at`) and, inside `kind: prompt`, one variant per collection mode, because the
`if`/`then` branches make the required and forbidden field sets mode-dependent. That is 12 variants:

| Variant | Required fields beyond the common core | Must not carry |
|---|---|---|
| `DevicePromptM0`, `StoredPromptM0` | `size_bytes`, `policy_decision` | digest, labels, classifier version, confidence, excerpt, attachments, window, detection basis |
| `DevicePromptM1`, `StoredPromptM1` | `size_bytes`, `policy_decision`, `content_digest`, `labels`, `classifier_version`, `confidence` | window, detection basis |
| `DevicePromptM2`, `StoredPromptM2` | as M1 plus `content_excerpt` | window, detection basis |
| `DevicePromptM3`, `StoredPromptM3` | as M1 | `content_excerpt`, window, detection basis |
| `DeviceUsageRollup`, `StoredUsageRollup` | `window_start`, `window_end`, `submission_count`, `bytes_total` | digest, labels, classifier version, excerpt, attachments, policy decision, `size_bytes`, detection basis |
| `DeviceModelDetection`, `StoredModelDetection` | `detection_basis` | digest, labels, classifier version, excerpt, attachments, policy decision, `size_bytes`, `window_start` |

`direction` is pinned per kind (`egress` for prompts, `none` for the other two), `kind` per variant, and
`collection_mode` per prompt variant.

### TypeScript (`typescript/envelope.ts`)

- `EnvelopeCore` holds the 13 fields every envelope must carry. Each variant interface extends it and
  declares only its own fields plus the narrowed discriminators.
- A field declared without `?` is required by the schema; `?` marks a field the schema permits but does
  not require; a field the schema forbids is absent from that interface.
- Enums are `as const` arrays (`KINDS`, `ROUTES`, ...) with the union type derived from the array
  (`export type Kind = (typeof KINDS)[number]`), so the runtime registry and the type cannot diverge and
  the registry is available at runtime for validation.
- Every field is `readonly` and every array is `readonly T[]`: an observation is immutable once built.
- `DeviceSubmission` and `StoredEnvelope` are the closed unions on `kind`.

### Go (`go/envelope/envelope.go`)

- `EnvelopeCore` holds the 13 core fields; each variant struct embeds it and declares only its own
  fields, so a field a kind must not carry cannot be compiled into that kind's record.
- A required field is a value field with no `omitempty`; a permitted-but-not-required field is a pointer
  with `omitempty`. An optional array is a pointer-to-slice (`*[]Attachment`) so that present-but-empty
  survives a round trip, which a plain slice with `omitempty` cannot express.
- `DeviceSubmission` and `StoredEnvelope` are sealed interfaces, one implementation per variant, each
  asserted at compile time.
- `DecodeStoredEnvelope` / `DecodeDeviceSubmission` dispatch on `kind` (and `collection_mode` inside
  prompts) and reject, by name: an unknown kind, an unknown mode, a missing required field, a field the
  kind must not carry, a field the contract does not declare (`DisallowUnknownFields`), and any
  constraint the schema states as `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `enum` or
  `const`. `Validate` on each type does the same for values built in Go rather than decoded.
- `format: uuid` / `format: date-time` are asserted as non-emptiness only; `pattern` constraints are
  enforced as written. Full JSON Schema validation of a record remains the ingest service's job.

## Notes the schema made ambiguous

These are recorded rather than resolved here, because the schema is the source of truth and editing it
is a contract change, not a generator change.

1. **`model_detection` permits three window fields.** Its branch forbids `window_start` but not
   `window_end`, `submission_count` or `bytes_total`, so those are emitted as optional on
   `DeviceModelDetection` / `StoredModelDetection`. ADR 0010's table says `model_detection` must not
   carry window fields at all, and `prompt` does forbid all four. If the intent is that they are
   forbidden, the schema's `not.anyOf` list needs those three names; regenerating then tightens the
   types automatically.
2. **`usage_rollup` permits `confidence`** (and `model_detection` too): it is not in either branch's
   forbidden list, so it is optional. That may be deliberate, since confidence is not content-derived.
3. **`received_at` is only forbidden, never required, by `deviceSubmission`.** Because a field cannot be
   both declared and forbidden in one JSON Schema object, the device variants simply do not declare it
   and the stored variants require it.
